# Wazuh Setup Guide

This guide documents the Wazuh side of the ClickFix detection lab used in this repository.

## Lab addresses used in the project

| Component | Address | Role |
|---|---:|---|
| Windows 11 victim | `10.0.2.15` | Wazuh Agent + Sysmon + PowerShell logging + ClickFixMonitor |
| Ubuntu Wazuh server | `10.0.2.6` | Manager + Indexer + Dashboard |
| Ubuntu AI server | `10.0.2.7` | Ollama + Qwen2.5:3B |

> If you reproduce the project with different IP addresses, update the Wazuh agent and `LLM/event1001_to_qwen.py` accordingly.

## 1. Prepare the Ubuntu Wazuh server

Update the Ubuntu VM:

```bash
sudo apt update
sudo apt upgrade -y
```

Install Wazuh Manager, Indexer, and Dashboard using the Wazuh all-in-one deployment for the version you intend to reproduce. This project used Wazuh `4.14.5`.

After installation, verify the main services:

```bash
sudo systemctl status wazuh-manager
sudo systemctl status wazuh-indexer
sudo systemctl status wazuh-dashboard
```

## 2. Enable JSON archives

Edit:

```bash
sudo nano /var/ossec/etc/ossec.conf
```

Inside the `<global>` block ensure:

```xml
<logall_json>yes</logall_json>
```

Restart the manager:

```bash
sudo systemctl restart wazuh-manager
```

Raw events will then be available in:

```text
/var/ossec/logs/archives/archives.json
```

Triggered alerts are stored in:

```text
/var/ossec/logs/alerts/alerts.json
```

## 3. Install the Windows Wazuh Agent

On the Windows 11 victim VM, install the Windows Wazuh Agent and point it to the manager:

```powershell
msiexec.exe /i wazuh-agent.msi /q WAZUH_MANAGER="10.0.2.6"
```

If the agent is registered manually, generate/import the agent key using the Wazuh manager and the Windows `manage_agents` utility.

The Windows configuration file is normally located at:

```text
C:\Program Files (x86)\ossec-agent\ossec.conf
```

## 4. Ensure required Windows event channels are collected

The final project relies on Windows Application events generated by `ClickFixMonitor`, plus Sysmon and PowerShell telemetry.

Useful event-channel entries are:

```xml
<localfile>
  <location>Application</location>
  <log_format>eventchannel</log_format>
</localfile>

<localfile>
  <location>Microsoft-Windows-Sysmon/Operational</location>
  <log_format>eventchannel</log_format>
</localfile>

<localfile>
  <location>Microsoft-Windows-PowerShell/Operational</location>
  <log_format>eventchannel</log_format>
</localfile>
```

Restart the Windows agent after configuration changes:

```powershell
Restart-Service wazuh
Get-Service wazuh
```

## 5. Verify agent connectivity

On the Wazuh manager:

```bash
sudo /var/ossec/bin/agent_control -lc
```

The Windows endpoint should appear as active.

## 6. Verify ClickFixMonitor Event ID 1001 reaches Wazuh

After generating a controlled ClickFixMonitor test event, check the raw archives:

```bash
sudo grep -i 'ClickFixMonitor' /var/ossec/logs/archives/archives.json | tail -20
```

Or filter Event ID 1001:

```bash
sudo grep -i '"eventID":"1001"' /var/ossec/logs/archives/archives.json | tail -20
```

## 7. Deploy the custom Wazuh rules

The repository contains the validated rule hierarchy in:

```text
Wazuh/local_rules.xml
```

On the manager, add the repository's ClickFix rule group to:

```text
/var/ossec/etc/rules/local_rules.xml
```

Do not blindly overwrite unrelated local rules that already exist on your system.

Validate the rule syntax and behavior:

```bash
sudo /var/ossec/bin/wazuh-logtest
```

Then restart Wazuh Manager:

```bash
sudo systemctl restart wazuh-manager
```

The project rule hierarchy is:

- `100100` — base ClickFixMonitor Event ID 1001 detection
- `100101` — HIGH-risk pre-execution event
- `100102` — strong PowerShell indicator condition

## 8. Verify alerts

Check:

```bash
sudo grep -E '100100|100101|100102' /var/ossec/logs/alerts/alerts.json | tail -20
```

At this point the flow should be:

```text
Windows Run dialog
        ↓
ClickFixMonitor
        ↓
Application Event ID 1001
        ↓
Wazuh Agent
        ↓
Wazuh Manager
        ↓
Custom rules 100100–100102
        ↓
alerts.json
```

## Important baseline note

The research baseline was evaluated before the custom ClickFix rule hierarchy was introduced. The default stack was used first so that collected telemetry could be compared with default alerts. Custom detection was then added as the improvement stage.
