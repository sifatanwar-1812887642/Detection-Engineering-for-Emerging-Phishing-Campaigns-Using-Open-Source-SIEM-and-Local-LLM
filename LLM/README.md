# Local LLM Setup — Ollama + Qwen 2.5 3B

This directory contains the local LLM integration used in the ClickFix detection engineering project. The local LLM runs on a separate Ubuntu VM and is used as an **analyst decision-support component** for Wazuh Event ID 1001 generated by `ClickFixMonitor`.

## 1. Lab Environment

| Component | Details |
|---|---|
| Wazuh Manager | Ubuntu 24.04 — `10.0.2.6` |
| Windows Victim / Wazuh Agent | Windows 11 — `10.0.2.15` |
| Local LLM Server | Ubuntu 24.04 — `10.0.2.7` |
| LLM Runtime | Ollama |
| LLM Model | `qwen2.5:3b` |
| Wazuh Version | 4.14.5 |
| Detection Event | Windows Application Event ID `1001` |
| Event Provider | `ClickFixMonitor` |

The VirtualBox lab uses a NAT Network so that the Wazuh Manager, Windows endpoint, and local LLM VM can communicate in the isolated research environment.

## 2. Integration Architecture

```text
Windows 11 Victim (10.0.2.15)
        |
        | ClickFixMonitor Event ID 1001
        v

        |
        v
Wazuh Manager (10.0.2.6)
        |

        v
```

> **Important:** The LLM output is advisory. Proposed detection logic is reviewed and validated by the analyst before being deployed as a Wazuh rule.

## 3. Install Ollama on Ubuntu 10.0.2.7

Log in to the Ubuntu VM used for the local LLM and install Ollama:

```bash
curl -fsSL https://ollama.com/install.sh | sh
```

Verify the installation:

```bash
ollama --version
```

## 4. Start and Enable the Ollama Service

Start Ollama and configure it to start automatically with Ubuntu:

```bash
sudo systemctl enable ollama
sudo systemctl start ollama
```

Check the service status:

```bash
sudo systemctl status ollama
```

The service should be shown as **active (running)**.

## 5. Download Qwen 2.5 3B

Pull the Qwen 2.5 3B model into the local Ollama installation:

```bash
ollama pull qwen2.5:3b
```

Verify that the model is available:

```bash
ollama list
```

The output should include:

```text
qwen2.5:3b
```

## 6. Test Qwen Locally

Run the model directly from the Ubuntu LLM VM:

```bash
ollama run qwen2.5:3b
```

Test with a simple prompt, for example:

```text
Explain ClickFix detection in one sentence.
```

Exit the interactive session when testing is complete.

## 7. Configure Ollama for the Wazuh Manager

By default, Ollama may listen only on the local host. The Wazuh Manager at `10.0.2.6` therefore needs Ollama to listen on the lab network interface.

Open the systemd service override:

```bash
sudo systemctl edit ollama
```

Add:

```ini
[Service]
Environment="OLLAMA_HOST=0.0.0.0:11434"
```

Save and exit, then reload systemd and restart Ollama:

```bash
sudo systemctl daemon-reload
sudo systemctl restart ollama
```

Verify that Ollama is listening on port `11434`:

```bash
ss -tulpn | grep 11434
```

The listener should show a network binding such as:

```text
0.0.0.0:11434
```

## 8. Test the Ollama API from the Wazuh Manager

From the Wazuh Manager (`10.0.2.6`), verify that the local LLM API is reachable:

```bash
curl http://10.0.2.7:11434/api/tags
```

A successful response should contain information about the installed model, including `qwen2.5:3b`.

Test actual generation from the Wazuh Manager:

```bash
curl http://10.0.2.7:11434/api/generate \\
  -d '{
    "model": "qwen2.5:3b",
    "prompt": "Explain ClickFix detection in one sentence.",
    "stream": false
  }'
```

If a generated response is returned, communication between the Wazuh Manager and Ollama is working.

## 9. Python Environment on the Wazuh Manager

The integration script runs on the Wazuh Manager and uses Python to read Wazuh archives and call the Ollama API.

Create a working directory and Python virtual environment:

```bash
mkdir -p ~/wazuh-ai
cd ~/wazuh-ai
python3 -m venv venv
source venv/bin/activate
```

Install the required Python package:

```bash
pip install -r requirements.txt
```

The repository's `requirements.txt` contains the HTTP client dependency used by the integration script.

## 10. Event ID 1001 to Qwen Integration

The script `event1001_to_qwen.py` is designed specifically for the project's ClickFixMonitor Event ID 1001.

It performs the following sequence:

1. Reads recent Wazuh `archives.json` records.
2. Filters for the Windows endpoint `10.0.2.15`.
3. Selects Event ID `1001`.
4. Confirms the provider is `ClickFixMonitor`.
5. Extracts the relevant event information.
6. Sends the event to the local Ollama API at `10.0.2.7:11434`.
7. Uses the `qwen2.5:3b` model for analysis.
8. Requests structured JSON containing the verdict, confidence, risk level, detection gap, observed indicators, and recommended Wazuh logic.
9. Converts validated indicators into a candidate PCRE2-based Wazuh rule.
10. Prints the proposed ruleset for analyst review.

The script is configured with:

```python
ARCHIVES_FILE = Path("/var/ossec/logs/archives/archives.json")
OLLAMA_URL = "http://10.0.2.7:11434/api/generate"
MODEL = "qwen2.5:3b"
TARGET_AGENT_IP = "10.0.2.15"
TARGET_EVENT_ID = "1001"
TARGET_PROVIDER = "ClickFixMonitor"
```

## 11. Run the Integration Script

On the Wazuh Manager:

```bash
cd ~/wazuh-ai
source venv/bin/activate
python3 event1001_to_qwen.py
```

The script searches for the latest applicable ClickFixMonitor Event ID 1001 and sends it to Qwen.

The expected processing flow is:

```text
Event 1001
   ↓
Event Extraction
   ↓
Qwen 2.5 3B Analysis
   ↓
Verdict + Confidence + Risk
   ↓
Observed Indicators
   ↓
Candidate Wazuh Ruleset
```

## 12. Example Event Used by the Project

A controlled pre-execution detection can contain information similar to:

```text
ClickFix Pre-Execution Detection
Target: Windows Run Dialog
Command Line: powershell -nop -w hidden -c whoami
Matched Indicators: powershell, -nop, -w hidden
Risk: HIGH
Detection Stage: Pre-Execution
```

The important point is that `ClickFixMonitor` records the suspicious command **before execution**, allowing the local LLM to analyze the detection event without assuming that execution, malware activity, network communication, or privilege escalation actually occurred.

## 13. Candidate Wazuh Rule Validation

The script generates a candidate ruleset based on the LLM analysis. The rules should **not** be deployed blindly.

First review the generated logic, then validate it using Wazuh's log testing facility:

```bash
sudo /var/ossec/bin/wazuh-logtest
```

Paste a representative Event ID 1001 log and confirm that the intended custom rule matches correctly.

After validation, the approved rule can be added to the Wazuh custom rules configuration and tested through the normal Wazuh alert pipeline.

## 14. End-to-End Test Procedure

For a complete laboratory test:

### Step 1 — Generate the ClickFix-style input

On the Windows 11 test endpoint, use the controlled Win+R scenario to place the test command into the Windows Run dialog.

### Step 2 — Pre-execution detection

`ClickFixMonitor` detects the suspicious content before execution and creates Windows Application Event ID 1001.

### Step 3 — Wazuh collection

The Wazuh Agent forwards the Windows event to the Wazuh Manager.

### Step 4 — Event archive

The event becomes available in the Wazuh archive data, including `archives.json`.

### Step 5 — LLM analysis

`event1001_to_qwen.py` selects the applicable Event ID 1001 and sends it to Ollama on `10.0.2.7`.

### Step 6 — Qwen analysis

Qwen 2.5 3B returns structured analyst-oriented findings.

### Step 7 — Rule suggestion

The script converts the validated indicators into candidate Wazuh rule logic.

### Step 8 — Analyst validation

The analyst reviews the proposed rule and tests it with `wazuh-logtest` before deployment.

## 15. Security and Lab Note

Ollama is configured to listen on `0.0.0.0:11434` so that the Wazuh Manager can access the model over the laboratory network. This configuration is intended for the isolated research environment.

For a production environment, access to the Ollama API should be restricted to trusted hosts and networks rather than exposing port `11434` broadly.
